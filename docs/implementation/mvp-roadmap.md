# MVP 范围与实施路线

## 1. 试点目标

首期选择一个专业、3～5 门课程、10～20 个实验项目和一个完整评价周期，打通：

> 材料导入 → 结构化审核 → 支撑关系 → 确定性评价 → 问题诊断 → 改进措施 → 复评准备

MVP 的目的不是覆盖全校，而是验证数据模型、评价可信度、教师工作流和安全边界。

## 2. MVP 功能范围

### 2.1 必须具备

- OIDC 登录、角色和专业/课程数据范围。
- 标准、毕业要求、指标点、课程和课程目标管理。
- 大纲、指导书、评分表和学生证据的受控上传。
- 异步解析、任务状态、失败重试和人工分类。
- 实验项目、评分项和能力要素的提取审核。
- 候选支撑关系的确认、驳回和版本管理。
- 版本化评价策略与确定性达成度计算。
- 从结果下钻到关系、评分项和来源证据。
- 问题、措施、责任人、期限和复评状态。
- 关键操作、下载、审批和模型调用审计。

### 2.2 可以后置

- 全校多租户运营。
- 通用自然语言报表设计器。
- 复杂知识图谱可视化编辑器。
- 自动同步所有教务系统。
- 移动端和学生端。
- Kubernetes 与微服务拆分。
- 大规模模型微调。

## 3. 实施阶段

### 阶段 0：领域与数据基线（约 2 周）

- 确认试点专业、课程、用户和评价周期。
- 固化术语、数据分级、材料清单和评价公式。
- 建立脱敏标注样本与验收集。
- 确认 OIDC、对象存储和校内部署条件。

退出条件：产品边界、数据字典、评价策略样例、安全责任人均获确认。

### 阶段 1：基础平台与材料导入（约 3 周）

- 建立 React、FastAPI、PostgreSQL、Redis、Worker 和对象存储基础工程。
- 完成登录、权限、文件上传、版本和任务工作台。
- 支持 PDF、DOCX 和扫描件的基础解析。

退出条件：授权用户能上传、查看任务、定位失败并访问受控文件；越权测试通过。

### 阶段 2：实验结构与关系审核（约 3 周）

- 提取课程目标、实验项目、评分项和能力要素。
- 建设人工审核界面。
- 建立正式关系、候选关系、来源引用和版本。
- 用标注集测量抽取和推荐效果。

退出条件：教师能够完成一个课程的结构化审核，正式关系均有依据和审核记录。

### 阶段 3：确定性评价（约 3 周）

- 实现评分导入、映射、评价策略和计算引擎。
- 保存输入快照、中间值、缺失率和结果。
- 建设从专业到课程、实验、评分项的下钻视图。
- 用人工样例进行双算核对。

退出条件：同一输入可稳定重算，系统结果与已确认人工样例一致。

### 阶段 4：AI 检索与辅助诊断（约 4 周）

- 建立脱敏分段和 pgvector 索引。
- 接入可替换模型适配层。
- 实现带引用问答、关系建议和异常解释。
- 建立模型评测、引用校验、审计和降级流程。

退出条件：AI 正式用途输出均有有效引用；无引用或越权上下文被阻断。

### 阶段 5：持续改进与试点验收（约 4 周）

- 实现问题、措施、责任人、期限和复评。
- 形成试点专业的完整闭环和认证支撑包。
- 完成安全测试、恢复演练、用户培训和运维交接。

退出条件：至少一个问题形成“发现—措施—复评准备”的完整记录，试点负责人签收。

## 4. 验收指标

### 4.1 正确性

- 已确认样例的评价计算一致率：100%。
- 正式评价可追溯到策略、输入和证据的比例：100%。
- 正式关系具备来源与审核记录的比例：100%。

### 4.2 AI 质量

- 在人工标注集上评估字段抽取准确率、关系建议准确率和引用有效率。
- 首期关系建议准确率目标可设为不低于 85%，但应在样本集完成后确认。
- 正式用途 AI 输出无有效引用时，进入人工待办而不是自动发布。

### 4.3 效率

- 对比人工基线，记录单门课程材料整理和证据定位用时。
- 记录教师接受、修改和驳回 AI 建议的比例。
- 记录解析失败率、人工复核量和任务平均时长。

### 4.4 安全与运维

- 关键越权场景阻断率：100%。
- 关键操作审计覆盖率：100%。
- 数据库与对象存储恢复演练成功。
- 生产配置和仓库无明文密钥。

## 5. 团队角色建议

- 产品/领域负责人：确认认证逻辑、术语、流程和验收。
- 前端工程师：材料、审核、评价和改进工作台。
- 后端工程师：领域模块、契约、评价引擎、权限和审计。
- 数据/AI 工程师：解析、检索、模型适配和评测。
- 测试工程师：契约、计算、权限、文件和端到端测试。
- 校方安全与运维：OIDC、网络、存储、备份和上线审批。

小团队可一人承担多个角色，但正式评价规则和安全审批不应只由开发人员单方面决定。

## 6. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 历史文档格式差异大 | 抽取准确率不稳定 | 先建代表性标注集，提供人工复核和失败队列 |
| 评价口径未统一 | 结果无法验收 | 阶段 0 固化样例、公式、阈值和缺失策略 |
| AI 被当作权威 | 产生错误正式关系 | 候选与正式数据分层，关键结果强制审核 |
| 学生数据外泄 | 严重合规风险 | 数据分级、脱敏、模型路由、权限过滤和审计 |
| 过早平台化 | 延误试点 | 限定一个专业和完整闭环，推迟微服务与全校运营 |
| 文件与数据库失配 | 引用失效 | 对象版本、内容哈希、事务补偿和一致性巡检 |
| 教师复核成本过高 | 使用意愿下降 | 优先展示低置信度和冲突项，支持批量确认与差异预览 |

## 7. 启动清单

开发开始前需要校方或项目负责人确认：

- 试点专业、课程和评价周期。
- OIDC 对接联系人及测试环境。
- 对象存储、数据库和模型的部署边界。
- 学生数据分级、保留期和外部模型政策。
- 一套可人工复算的评价样例。
- 可用于开发测试的脱敏材料和标注责任人。
