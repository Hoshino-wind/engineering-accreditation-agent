# 项目分析与产品边界

## 1. 项目定位

工程认证智能体不是一个“让大模型替老师写认证材料”的工具，也不是一套通用认证流程管理系统，而是一套面向实验教学的能力图谱构建、智能分析与持续改进平台。

系统把分散在培养方案、课程大纲、实验指导书、评分表、学生报告和改进记录中的信息，组织成可计算、可验证的实验教学能力图谱：

> 认证标准 → 毕业要求 → 指标点 → 课程目标 → 实验项目 → 评分规则 → 学生证据 → 达成度 → 问题 → 改进措施 → 复评

产品逻辑是：

> 材料是输入，能力图谱是核心资产，分析与评价是决策机制，持续改进是闭环，工程认证支撑是输出。

平台的核心价值有四点：

1. **能力关系清楚**：说明某个实验为什么存在、培养什么能力、涉及什么知识和技能、由什么评分项评价。
2. **图谱结论可信**：正式节点和关系有版本、有来源、有审核，可回到材料原文。
3. **评价计算可信**：达成度计算可复现、可解释、可回溯到公式、图谱版本和原始证据。
4. **教学改进闭环**：从发现问题到修改教学对象、更新图谱，再到下一轮复评，形成连续记录。

## 2. 目标用户

### 2.1 实验教师

- 导入课程大纲、指导书、评分表和学生报告。
- 审核系统提取的实验项目、知识点、能力点和评分规则。
- 查看课程目标、实验项目和评价证据之间的缺口。
- 发起或确认课程层面的改进措施。

### 2.2 专业负责人和认证工作组

- 管理标准、毕业要求、指标点和培养方案版本。
- 审核跨课程支撑关系和证据完整性。
- 查看专业层面的达成度、异常和持续改进闭环。
- 导出带来源引用的认证支撑材料。

### 2.3 教学管理人员

- 管理专业、学期、课程、教师、角色和数据范围。
- 监控材料完整性、任务状态和审核进度。
- 查看操作日志、下载日志和模型调用记录。

### 2.4 学生

首期不建设学生操作端。学生是证据数据主体，不是主要使用者；如后续开放，应独立进行隐私评估和产品设计。

## 3. 当前主要问题

### 3.1 能力要素表达不统一

同一能力可能在课程大纲、实验目标、评分表中使用不同表述，人工梳理耗时且容易产生歧义。

### 3.2 支撑关系散落在文档中

毕业要求、课程目标、实验项目和评分项之间缺少统一的数据模型，关系常以表格、段落或经验存在。

### 3.3 材料之间缺少一致性检查

课程大纲、实验指导书和评分表可能对同一实验的目标、内容、分值和能力要求表述不一致，现有工具难以主动发现冲突。

### 3.4 材料与评价脱节

实验报告数量多，但“哪份材料支撑哪项能力、哪一条评分规则”通常不明确，抽查和复核成本高。

### 3.5 达成度缺乏版本和依据

公式、阈值、样本、缺失处理和课程版本若未固化，评价结果难以重现，也难以比较不同周期。

### 3.6 持续改进停留在文字总结

问题、措施、责任人、完成时间、复评结论缺少结构化关联，难以证明改进真正闭环。

## 4. 产品能力

产品能力按业务事实和状态流转拆分，完整定义见[功能模块产品总图](modules/README.md)。

产品由八个业务模块和一个系统治理模块组成：

| 编号 | 模块 | 深度 | 核心职责 |
| --- | --- | --- | --- |
| M1 | 总览与任务工作台 | 简做 | 汇总专业、周期、图谱建设进度、失败任务和业务待办 |
| M2 | 实验教学能力图谱 | 重点细做 | 拥有正式节点、关系、版本、来源和影响链 |
| M3 | 教学资源与材料 | 产品适中、底层细做 | 管理文件、资源版本、解析、脱敏和可定位证据 |
| M4 | 智能识别与映射审核 | 重点细做 | 识别节点与关系候选，并由教师审核后提交图谱 |
| M5 | 图谱分析与一致性诊断 | 重点细做 | 检查覆盖缺口、材料冲突、结构问题和版本影响 |
| M6 | 达成度评价与统计 | 最重点细做 | 用版本化确定性策略生成可复算评价结果 |
| M7 | 教学优化与持续改进 | 重点细做 | 将问题落实为教学对象变更，并通过复评验证效果 |
| M8 | 工程认证支撑 | 简做 | 汇总正式事实，生成带来源和审批记录的固定支撑材料 |
| M9 | 系统治理 | 页面简做、底层严格 | 统一身份、数据范围、权限、模型政策和审计 |

AI 是嵌入 M3～M7 的辅助能力，不单独建设产品模块或聊天入口。它可以生成带引用的候选、解释和草稿，但不能直接产生正式图谱关系、评价数值或改进结论。

模块通过正式版本、稳定对象 ID 和状态门槛交接，详细正向流程、回退路径和首个验收场景见[端到端业务闭环](end-to-end-closed-loop.md)。

## 5. 关键业务原则

### 5.1 AI 建议不等于正式事实

AI 可以提出“该实验可能支撑某指标点”的候选关系，但只有经授权人员确认后，才能成为正式关系。

### 5.2 评价计算不交给大模型

大模型可解释结果、总结原因，但不能直接生成正式达成度。正式数值由版本化公式和确定性程序计算。

### 5.3 所有结论都应可回溯

正式关系、评价结果和改进结论应追溯到数据版本、文件片段、计算策略、操作者和时间。

### 5.4 图谱是核心业务模型，不是展示效果

图谱必须服务于路径追溯、覆盖分析、一致性诊断、达成度评价和影响分析，不以可视化连线数量衡量价值。首期权威关系使用 PostgreSQL 关系表保存，pgvector 只负责召回相似内容和辅助发现候选关系。

## 6. 首期不做

- 不自动替代教师审批正式支撑关系。
- 不让大模型直接修改成绩或正式评价结果。
- 不建设通用教务系统、排课系统、项目管理平台或在线实验平台。
- 不建设独立 AI 聊天入口。
- 不把复杂图数据库或自由拖拽图谱编辑器作为首期前置条件。
- 不在首期引入微服务和 Kubernetes。
- 不承诺一次导入即可完全正确识别所有历史材料。
- 不把真实学生材料提交到公共代码仓库。

## 7. 成功标准

- 一项正式评价能够追溯到公式版本、输入数据和证据文件。
- 正式图谱节点和关系具备有效来源、审核决定和适用版本。
- 一项诊断发现能够追溯到规则、图谱版本和材料证据。
- 认证工作组可以从专业层面下钻到课程、实验和证据。
- AI 生成的正式用途内容具备来源引用，关键结论经过人工确认。
- 改进事项能够关联到问题、实际教学对象变更、图谱更新和下一轮复评结果。
