# M7 教学优化与持续改进

## 1. 模块定位

本模块把图谱诊断、评价异常、证据缺口和结构问题转化为可执行教学改进，并在后续周期通过图谱更新和复评判断措施是否有效。

问题不能仅凭“措施已完成”关闭；关闭必须有复评或经批准的终止依据。

## 2. 用户结果

- 教师能够从评价结果或证据缺口快速建立问题。
- 每个问题都有原因、措施、负责人、期限和验证方法。
- 措施可以落实为课程目标、实验项目、教学资源、图谱关系或评分规则的新版本。
- 后续周期能够自动提醒复评并记录有效性结论。
- 专业负责人可以看到问题是否真正形成闭环。

## 3. 参与角色

- 课程负责人：确认课程层问题和原因。
- 改进责任人：制定并执行措施。
- 专业负责人：批准高影响措施和关闭结论。
- 评价负责人：提供基线结果并执行复评。
- 认证工作组：监督期限、效果和跨周期闭环。

## 4. 核心对象

| 对象 | 说明 |
| --- | --- |
| `QualityIssue` | 证据缺口、结构冲突、评价未达标或数据问题 |
| `RootCauseAnalysis` | 原因分类、说明和依据 |
| `ImprovementAction` | 措施、负责人、期限和目标 |
| `ActionChangeRef` | 关联课程、实验、材料或评分规则变更 |
| `VerificationPlan` | 验证方法、目标指标和复评周期 |
| `Reevaluation` | 后续周期结果和有效性判断 |
| `ClosureDecision` | 关闭、继续或升级决定 |

## 5. 主流程

1. 用户从评价结果、覆盖缺口或材料异常创建问题。
2. 系统带入来源对象、基线值和影响范围。
3. 课程负责人确认问题并完成原因分析。
4. 责任人制定一个或多个措施和验证计划。
5. 专业负责人按影响范围审批措施。
6. 责任人执行措施并创建实际教学对象的新版本。
7. M2 更新受影响图谱，M5 重新执行诊断。
8. 系统在目标周期生成复评待办。
9. 评价负责人关联新的评价运行。
10. 系统对比基线、图谱变化、目标和复评结果。
11. 负责人判断有效、部分有效或无效，并决定关闭或继续。

## 6. 状态与规则

```text
open
  → diagnosing
  → action_planned
  → approved
  → in_progress
  → awaiting_reevaluation
  → effective / partially_effective / ineffective
  → closed 或 revised_action
```

- 问题必须引用来源事实，不接受无来源的正式问题结论。
- 措施必须有负责人、期限、目标和验证方法。
- “已完成措施”不等于“问题已解决”。
- `effective` 才可直接进入关闭审批。
- `partially_effective` 和 `ineffective` 默认要求修订或新增措施。
- 关闭后保留完整问题、措施、变更和复评记录。
- 跨周期比较必须固定两次评价运行的版本。

## 7. 输入与输出

上游输入：

- [图谱分析与一致性诊断](05-graph-analysis-diagnosis.md)的已确认问题；
- [达成度评价与统计](06-attainment-evaluation.md)的未达标和异常结果；
- [教学资源与材料](03-teaching-resources.md)的证据质量问题。

向下游输出：

- 已确认问题和原因；
- 已批准措施与验证计划；
- 关联变更；
- 复评结论和关闭决定；
- 返回 [实验教学能力图谱](02-ability-graph.md)的新版本引用；
- 可进入 [工程认证支撑](08-accreditation-support.md)的改进闭环证据。

## 8. 页面范围

- 问题列表和来源下钻。
- 原因分析和措施制定。
- 负责人、期限、提醒和审批。
- 措施执行证据与关联变更。
- 图谱变化前后对比。
- 复评对比和有效性判断。
- 专业级闭环看板。

## 9. 非目标

- 不建设通用项目管理或工单系统。
- 不允许仅上传总结文字就关闭问题。
- 不由 AI 自动判断措施有效性。
- 不覆盖评价模块的计算和审批职责。

## 10. 验收标准

- 至少一个未达标结果能够建立问题并保留来源。
- 问题具备原因、措施、负责人、期限和验证计划。
- 措施完成后不会自动关闭问题。
- 后续评价运行能够与原问题和措施建立关联。
- 改进措施能够关联实际教学对象和图谱新版本。
- 关闭问题均具备复评结论或批准的终止依据。
- 问题闭环率、逾期率和措施有效率可统计。

## 11. 当前 PC 原型切片

当前 `/improvements` 已实现 1920×1080 Ant Design PC 工作台，用一屏串联“问题—措施—实际变更—图谱更新—复评—判效”：

- 顶部展示问题总数、执行中、待复评和待判效数量，均明确标记为试点示例数据。
- 左侧问题队列支持按 M3/M5/M6 来源、状态和关键词筛选。
- 中部展示来源事实、根因、已批准措施、负责人、期限、目标、验证方式，以及实际教学资源、评分规则和图谱版本。
- 右侧固定比较基线、目标、复评和差值，并逐项显示关闭门槛。
- 来源对象、证据哈希、实际变更 ID、图谱版本和复评运行可在追溯抽屉中完整查看。
- 有效、部分有效和无效均由人工选择；草稿跨刷新保留，提交动作进入 M9 本地审计轨迹，AI 不自动形成结论。
- `/improvements?case=<问题ID>` 可直接定位指定改进问题；手动切换问题会同步稳定地址，刷新和浏览器历史导航可恢复对象上下文，无效 ID 会提示并回退到当前可处理问题。

试点主案例为 `QI-2026-017 工程规范与伦理未达标`：来源为 M6 评价运行，基线 `0.68`，目标 `0.75`，复评 `0.73`；措施已关联《网络工程案例指导书》`v2.0`、伦理风险分析 Rubric `v1.1` 和图谱 `v0.4` 草稿，当前等待负责人判断有效性。

### 11.1 已固化的关闭规则

前端纯规则 `assessImprovementClosure` 当前检查：

1. 来源对象和证据哈希存在；
2. 根因、负责人、期限、目标、验证方法和措施审批完整；
3. 至少关联一个已审核的实际教学对象新版本，并关联图谱新版本；
4. 关联后续复评运行；
5. 形成人工有效性结论。

只有全部检查通过且结论为 `effective` 时，才具备“申请关闭”的业务条件。措施已完成但没有复评时不能关闭；`partially_effective` 或 `ineffective` 必须修订或新增措施。以上规则已有自动化测试。

## 12. 当前边界与后续接口

- 当前页面使用 `prototypeOnlyImprovementCases`，不伪装成服务端持久化数据。
- 当前对象级地址只编码改进问题稳定 ID，不在 URL 中复制有效性草稿、关闭结论或权限状态。
- “新建改进问题”和“提交结论”已提供本地可运行闭环，并明确记录为本地草稿/审计事件，不代表服务端正式写入。
- 正式数据、审批、提醒、复评待办和关闭决定仍归后端 `improvements` 模块。
- 后续 API 应首先提供问题列表/详情、措施审批、变更引用、复评关联和关闭申请；服务端必须重复执行关闭门槛，不能信任前端按钮状态。
- 接入写操作前必须完成 OIDC、专业/课程数据范围和追加审计事件。
